# 🎥 동영상 시연 대본 및 행동 매핑 명세서 (상세 확장판)

시연 동영상(약 9분)은 앱의 핵심 가치인 **"기억(Record) ➔ 계획(Plan) ➔ 새로운 기억(Record)"**의 순환 구조와 **소셜 상호작용**을 바탕으로 5단계로 진행됩니다. 본 대본은 누구나 이해하기 쉬운 **대중적 설명**과 심사위원을 위한 **전문 기술 용어**를 교차 사용하여 기술적 완성도와 기획의도를 동시에 전달하도록 세밀하게 구성되었습니다.

---

## 🏗️ Phase 0: 프로젝트 필수 기술 스펙 (도입부 언급 권장)
본격적인 시연에 앞서, 프로젝트 전체를 지탱하는 비기능 요건과 기획 의도를 심사위원들에게 명확히 각인시킵니다.

> **[필수 기술 지식 요약]**
> * **도커 및 REST API 아키텍처**: "본 프로젝트의 백엔드는 **도커(Docker) 컨테이너 환경**에서 Spring Boot와 MySQL을 기반으로 구축되었으며, 클라이언트와 서버는 완벽히 분리된 **REST API 아키텍처**로 통신합니다. 총 41개의 API가 정의되어 있으며, 프론트엔드는 Retrofit2를 통해 비동기로 데이터를 주고받습니다."
> * **카카오 API 도입 의도**: "구글 맵스 대신 카카오 로컬 API를 채택한 이유는 한국의 세밀한 상호명과 골목 단위 위치 정보를 더 정확하게 반환받아 AI에게 주입하기 위함입니다."
> * **리스트 렌더링 의도**: "소셜 기능이나 목록에서 다량의 일기/계획 데이터를 불러올 때 발생하는 메모리 누수와 속도 저하를 막기 위해, 안드로이드의 **RecyclerView 뷰홀더(ViewHolder) 패턴**을 철저히 적용하여 뷰를 최적화 및 재사용했습니다."
> * **네트워크 이미지 안정성 (Glide 적용)**: "외부 네트워크 이미지를 불러올 때 발생할 수 있는 메모리 크래시와 렌더링 깨짐 현상을 방지하기 위해, Glide 라이브러리를 커스텀한 `ImageUtil`을 전역적으로 도입하여 생명주기(Lifecycle) 충돌 없이 안정적인 이미지 표출을 구현했습니다."

## 🗄️ Phase 0-1: 핵심 ERD 및 스키마 설계 의도 (사전 설명)
시연 전, 본 앱의 거대한 데이터 사이클(기록➔계획➔기록)과 소셜 기능을 완벽히 지탱하는 **총 8개의 전체 테이블 구조**를 3가지 그룹으로 나누어 상세히 설명합니다.

> **[전체 8개 테이블: User, Diary, DayPlan, Place, Friend, FriendRequest, Reaction, Comment]**
> "저희 서비스의 데이터베이스는 8개의 테이블로 설계되었으며, 이를 3가지 핵심 도메인 그룹으로 나누어 설명하겠습니다.
> 
> **1. [계정 도메인: `User`]**
> 계정 및 인증의 단순화를 위해, `User` 테이블은 복잡한 비밀번호 필드 없이 `String id`를 기본키(PK)로 사용합니다. 이 구조는 소셜 기능 확장에 필수적인 고유 ID 매핑을 직관적이고 가볍게 처리하기 위한 핵심 기반입니다.
> 
> **2. [기록 및 AI 동선 도메인: `Diary`, `DayPlan`, `Place`]**
> 이 그룹은 다이어리와 여행 계획의 하이브리드 결합을 담당합니다. 
> * **`Diary`**: 과거의 일기와 미래의 여행 계획을 별도 테이블로 파편화하지 않고 하나에 담되, 핵심 필드인 `is_plan(boolean)` 플래그를 두어 데이터를 완벽히 분리합니다.
> * **`DayPlan` & `Place`**: AI가 생성한 여행 동선의 계층화입니다. `Diary`는 1:N으로 `DayPlan(일차)`을, `DayPlan`은 1:N으로 `Place(장소)`를 가집니다. 특히 `Place` 테이블은 AI가 계산한 이동 시간(`travel_time`)과 사용자의 드래그 앤 드롭 순서를 영구 저장하는 정렬 값(`sequence`) 필드를 가집니다. 이 계층 구조 덕분에 JPA의 고아 객체 제거(`orphanRemoval`) 로직이 완벽하게 작동하여 잦은 수정 시 데이터 찌꺼기를 방지합니다.
> 
> **3. [소셜 네트워크 도메인: `Friend`, `FriendRequest`, `Reaction`, `Comment`]**
> 이 그룹은 확장성 높은 사용자 간 양방향 소셜 기능 전체를 관장합니다.
> * **`Friend` & `FriendRequest`**: 모두 `User` 테이블의 ID를 외래키(FK)로 참조하여, 친구 요청의 승인/대기 상태(`status`)부터 최종 양방향 연동까지 안정적으로 관리합니다.
> * **`Reaction` & `Comment`**: 친구의 다이어리나 여행 계획에 하트를 누르거나 댓글을 남기는 기능을 처리하기 위해, 각각 `User`와 `Diary`를 N:1로 참조하도록 설계하여 실시간 소셜 상호작용의 데이터 무결성을 보장합니다."

## 📌 Phase별 시나리오 및 상세 대본

### 🎬 Phase 1: 첫 인상 - 기록과 계획의 공존 (1분)
* **화면**: 메인 홈(`HomeFragment`) 달력 및 통계 화면.
* **프론트엔드 액션**: 앱 실행 후, 달력의 마커(초록/주황)와 상단 통계(스트릭) 뷰를 번갈아 가리킵니다.
* **설명 대본 (대중 + 전문용어 결합)**: 
  > "Harudiary는 내 소중한 **'과거의 일기'**를 바탕으로 **'미래의 여행'**을 설계해주는 똑똑한 다이어리입니다. 달력을 보시면 초록색 점은 제가 작성한 과거의 일기, 주황색 점은 앞으로 갈 미래의 여행 계획을 의미하여 **색깔별로 한눈에 구분(분리 렌더링)**되도록 화면에 나타납니다. 
  > 여행 계획은 아직 가기 전의 미래 정보이기 때문에, 꾸준함을 보여주는 **'연속 작성 기록(스트릭 통계)'**에는 영향을 주지 않아야 합니다. 이를 위해 백엔드 DB 단에서 별도의 테이블을 파편화하지 않고, **동일한 스키마(Diary 테이블)를 공유하면서도 `is_plan` 플래그를 두어 기록과 계획을 완벽히 구분**했습니다.
  > **[UX 유용성]**: 덕분에 사용자는 달력만 보고도 과거의 추억과 다가올 설렘을 직관적으로 파악할 수 있으며, 일기 작성 습관(스트릭)을 훼손받지 않아 매일 꾸준히 기록을 남기려는 강력한 동기부여를 얻을 수 있습니다."

### 🎬 Phase 2: 내 주변 추천과 스마트 에디터 - 알아서 채워주는 일기 (2분)
* **화면**: 홈 ➔ 일일 타임라인 ➔ 다이어리 작성 화면 (`RecordActivity`)
* **프론트엔드 액션**: 홈 화면에서 **[내 주변 즉석 추천]** 버튼을 눌러 현재 날씨 기반 AI 타임라인을 확인합니다. 이후 메인으로 돌아와 중앙의 **[+] 버튼**을 눌러 일기 작성 창에 진입합니다. 위치와 날씨가 자동으로 채워지는 것을 보여주며, 위치 정보 필드는 의도적으로 수정이 불가능함을 가리킵니다.
* **하위 세부 로직 (프론트엔드 의도)**: 
  1. (추천 로직): 기상청 API 날씨 데이터를 AI에게 주입하여 컨텍스트 기반 동선 제공.
  2. (기록 로직): 위치 정보 수정 불가(고정된 제목화) 원칙. 사용자가 다녀온 기록의 '정체성'을 보존하기 위해 위치 필드를 강제 고정.
* **설명 대본 (대중 + 전문용어 결합)**: 
  > "먼저, 홈 화면의 **[내 주변 즉석 추천]**을 누르면, 기상청 API로 현재 비가 오는지 등의 날씨 상황을 파악해 AI가 실내 위주로 즉석 동선을 짜주는 것을 볼 수 있습니다. 
  > 추천뿐만 아니라, **[+] 버튼**을 눌러 내 일기를 직접 기록할 때도 스마트합니다. 일기를 쓸 때마다 주소나 날씨를 입력할 필요 없이, 앱이 **주소 자동 변환 시스템(카카오 역지오코딩 및 기상청 API 융합)**을 거쳐 자동으로 찾아줍니다. 여기서 눈여겨보실 점은 위치 정보가 '수정 가능한 텍스트'가 아니라 기록의 고유 정체성을 나타내는 '고정된 제목'으로 처리된다는 점입니다. 나의 진짜 발자취를 임의로 훼손하지 않으려는 프론트 로직의 기획 의도를 담았습니다.
  > **[UX 유용성]**: 이러한 자동 채우기와 위치 고정 원칙 덕분에, 사용자는 나중에 일기를 다시 펼쳐보았을 때 **'아, 내가 이때 비 오는 날 이 카페에 있었구나'**라며 언제, 어디서, 무엇을 했는지 왜곡 없이 정확하게 회상할 수 있는 강력한 추억 보관소를 얻게 됩니다."

### 🎬 Phase 3: 소셜 기능 - 친구의 계획 엿보기와 즉각적 피드백 (1분 30초)
* **화면**: 친구 탭(`FriendListFragment`) ➔ 내 타임라인 조회 ➔ 친구 프로필 ➔ 친구의 최신 일기/계획 상세 조회
* **프론트엔드 액션**: 내 타임라인을 스크롤하며 무의미했던 별점(⭐) 대신 **친구들이 눌러준 하트(❤️) 개수가 전면 배치**된 것을 보여줍니다. 이후 친구 탭에서 오늘 친구가 올린 새로운 여행 계획을 누르고, 하단의 **'하트'**를 누르거나, **'나도 갈래!'**라는 댓글을 입력하여 실시간 연동을 시연합니다.
* **하위 세부 로직 (프론트엔드 의도)**: RecyclerView ViewHolder 패턴 적용 및 41개 REST API 중 15개를 소셜 네트워크 통신(양방향 동기화)에 할당. 특히 별점 시스템을 과감히 폐지하고 소셜 피드백(하트)을 뷰홀더 전면에 내세우는 UX 개편.
* **설명 대본 (대중 + 전문용어 결합)**: 
  > "혼자 쓰는 일기를 넘어 친구와 소통할 수도 있습니다. 도커 REST API 환경 위에 15개의 전용 소셜 API를 구축해 양방향 통신을 지원합니다. 저희는 기존의 무의미한 별점(⭐) 시스템을 완전히 폐지하고, 그 자리에 **'친구가 눌러준 하트(❤️) 개수'가 전면 표출되도록 렌더링 로직을 개편**했습니다. 내 일기 리스트나 타임라인을 넘겨볼 때마다 친구들이 얼마나 반응을 보였는지 직관적으로 볼 수 있으며, 친구가 내 일기에 하트나 댓글을 남기면 숨어있던 '리액션 바(Reaction Bar)'가 스르륵 팝업되며 즉각적인 피드백을 눈으로 확인할 수 있죠.
  > 단절된 일기장을 넘어 여행이라는 공통 관심사로 실시간 소셜 상호작용의 데이터 무결성을 보장하는 저희만의 확장성입니다.
  > **[UX 유용성]**: 사용자 입장에서는 지인들의 실제 다녀온 기록이나 갈 계획을 구경하며 '다음엔 나도 저기 가봐야지' 하는 영감을 얻고, 단순한 일기 쓰기를 넘어 서로 공감하고 소통하는 즐거움을 누릴 수 있습니다."

### 🎬 Phase 4: 핵심 기능 - 일기가 여행이 되는 순간 (2분 30초)
* **화면**: 목록 탭 ➔ 과거 일기(`RecordActivity`) 조회 ➔ 여행 추천 대기 화면 ➔ `TravelPlanActivity`
* **프론트엔드 액션**: 과거 작성한 '제주도 흑돼지' 일기를 클릭, 하단 **[✨ AI 여행계획 생성]** 클릭. 새로운 AI 추천 창으로 넘어갈 때 과거 일기의 '장소(주소)'와 '본문 내용'이 프롬프트 입력창에 **자동으로 꽉 채워진 것(제로 타이핑)**을 보여줍니다. 이후 스피너 대기를 거쳐 최종 여행 일정 화면을 표출합니다.
* **하위 세부 로직 (프론트엔드 의도)**: 외부 API 맹점 극복을 위한 다중 호출, 인텐트(Intent)를 활용한 프롬프트 자동 주입(Zero-Typing), Gemini 맵 그라운딩(Map Grounding) 연동.
* **설명 대본 (대중 + 전문용어 결합)**: 
  > "이제 Harudiary만의 마법을 보여드리겠습니다. 예전에 갔던 '제주도 흑돼지 맛집' 일기를 클릭하고 하단의 **[✨ AI 여행계획 생성]** 버튼을 누릅니다. 보시는 것처럼 과거 다이어리의 **위치 정보(주소)와 내 기록(본문)이 새로운 AI 입력 프롬프트에 인텐트(Intent)를 통해 그대로 자동 주입**됩니다. 번거롭게 타이핑할 필요조차 없죠(제로 타이핑). 곧바로 [생성]만 누르면, AI가 그 맛집 주변의 카페, 숙소까지 포함된 풀코스 여행 일정을 알아서 짜줍니다.
  > 기존 외부 추천 시스템이 관광지로만 쏠리는 것을 막기 위해, 백엔드에서 **AI 맞춤형 정보 수집 시스템(다중 카카오 로컬 API 호출 및 카테고리 풀 융합)**을 적용했습니다.
  > 여기서 중요한 점은, AI가 단순히 텍스트를 뱉는 것이 아니라 프론트엔드와 완벽히 통신하도록 엄격한 JSON 형식(`day_number`, `place_name`, `travel_time`)으로 응답하게 설계되었다는 점입니다. 이 JSON 데이터가 안드로이드 RecyclerView에 매핑되어 장소 카드로 변환되고, `travel_time`은 카드 사이를 잇는 '이동 시간 선'으로 시각화되어 화면에 나타납니다. 
  > 이렇게 복잡한 내비게이션 연동 없이도 **최적의 동선과 이동 시간을 찾아줄 수 있는 이유는 제미나이(Gemini) API 내부의 '맵 그라운딩(Map Grounding)' 기능과 직접 연동**되도록 설정했기 때문입니다. 덕분에 동선을 짜는 수고를 획기적으로 덜어줍니다.
  > **[UX 유용성]**: 사용자는 번거로운 타이핑 없이 '내가 직접 갔고 좋았던 그 장소'를 중심으로 한 나만의 맞춤형 풀코스를 단 1분 만에 선물 받게 됩니다. 블로그나 지도를 수십 번씩 켜가며 동선을 짜던 엄청난 스트레스와 시간 낭비가 완벽히 사라지는 순간입니다."

### 🎬 Phase 5: 편집과 방어 로직 & 순환 구조 피날레 (2분)
* **화면**: 목록 탭/타임라인(`DailyTimelineFragment`) ➔ `TravelPlanActivity` 내부 RecyclerView ➔ 목록 일괄 삭제 화면(`DeleteRecordsActivity`)
* **프론트엔드 액션**: 내 목록에서 각 카드 우측 상단의 **휴지통(🗑) 아이콘을 눌러 즉시 개별 삭제되는 것**을 보여줍니다. (반대로 친구 다이어리에서는 이 버튼이 보이지 않음을 어필합니다.) AI 플랜 장소 카드를 위아래로 **드래그**하여 순서를 변경하고, 왼쪽으로 **스와이프**하여 삭제를 시연합니다. [저장] 버튼을 누른 후, [✅ 방문 인증] 버튼을 눌러 일기로 굳히는 피날레를 보여줍니다. 이후 휴지통 일괄 삭제 시연도 진행합니다.
* **하위 세부 로직 (프론트엔드 의도)**: RecyclerView ItemTouchHelper, 권한 기반 접근 제어(RBAC) UI 분리 로직, Zero Logic Deletion, View Type 필터링, 그리고 무한 순환 구조(Record ➔ Plan ➔ Record).
* **설명 대본 (대중 + 전문용어 결합)**: 
  > "Harudiary는 철저한 사용자 보호 장치를 겹겹이 설계했습니다. 리스트나 타임라인의 각 카드 우측 하단 휴지통 아이콘(🗑)을 누르면 그 자리에서 즉시 다이어리 삭제가 가능하며 RecyclerView에서 스르륵 사라집니다. 더욱 중요한 점은, **내 일기가 아닌 친구의 다이어리를 열람할 때는 이 휴지통 아이콘이 아예 노출되지 않도록 철저한 View 권한 분리(RBAC 접근 제어) 로직**이 적용되어 있다는 점입니다.
  > AI가 짠 일정도 마찬가지입니다. 내 마음대로 순서를 바꾸거나 뺄 수 있습니다. 손가락으로 밀거나 끌어서(Drag & Swipe) 아주 직관적으로 수정할 수 있죠. 이렇게 빈번한 수정이 일어나도 **데이터 찌꺼기 없는 깔끔한 관리(JPA `orphanRemoval=true` 기반 고아 객체 정리 및 트랜잭션 무결성)**를 통해 불필요한 용량 누수를 완벽히 차단합니다. 
  > 일정을 수정한 후 **[저장]을 누르면, 변경된 순서와 삭제 내역이 다시 JSON으로 패키징되어 DB에 덮어씌워지며 완벽히 확정**됩니다.
  > 또한, 일기를 일괄 정리하다가 발생할 수 있는 실수 방지를 위해, 휴지통 화면에서는 내 소중한 '여행 계획'은 아예 노출되지 않도록 **Zero Logic Deletion 및 View Type 필터링 방어 로직**을 두었습니다. 
  > **[마무리 피날레]**: 마지막으로, 확정된 계획의 장소를 실제로 방문한 뒤 **[✅ 방문 인증]** 버튼을 누르면, 이 장소는 또 하나의 새로운 '실제 일기 객체'로 영구 저장됩니다. 사용자는 이 일기를 바탕으로 또 다른 AI 여행을 계획할 수 있어, 앱 내에서 **[기록 ➔ 계획 ➔ 기록]의 무한한 순환 구조**가 완성됩니다!
  > **[UX 유용성]**: 사용자는 실수로 휴지통에서 소중한 일정을 날리거나 타인의 기록을 건드릴 걱정 없이 마음 편히 앱을 관리할 수 있습니다. 무엇보다 여행이 끝난 직후 버튼 하나로 그 계획이 다시 '일상의 기록'으로 굳어지고, 그 기록이 또 다른 설레는 여행을 낳는 이 거대한 순환이야말로, 사용자가 우리 앱을 '평생의 여행 파트너'로 삼게 만드는 가장 강력한 이유입니다."

## 🛠️ 실시간 시연 시 데이터 조작 순서 (업데이트 버전)

위 대본의 흐름에 맞게, 10개의 데이터가 자동 주입된 환경(`inject_demo_data.py` 실행 완료 후)에서 시연자가 직접 조작할 6가지 핵심 Action 요약입니다.

| 순서 | 시연 화면 (UI) | 수행 동작 (Action) | 목적 (Key Message) |
| :--- | :--- | :--- | :--- |
| **1** | 메인 홈 | 달력 마커(초록/주황) 및 상단 스트릭 가리키기 | 과거와 미래 데이터의 명확한 구분 및 통계 무결성 설명 (`is_plan` 플래그 적용 증명) |
| **2** | 타임라인/친구 | 내 타임라인 카드에 렌더링된 **하트(❤️) 개수**를 어필 ➔ 친구 탭에서 최신 계획 클릭 ➔ 하트 누르고 댓글에 "나도 갈래!" 입력 | 별점 시스템 폐지 후 도입된 직관적인 소셜 리액션(하트 표출) 및 REST API 기반 양방향 통신 확장성 시연 |
| **3** | 작성 화면 | `+` 버튼 클릭 ➔ 위치/날씨 자동 입력 부분 가리키고, 위치 필드가 고정되어 있음(수정 불가)을 탭해서 보여줌 | 스마트 에디터의 편의성 및 데이터 정체성(Identity) 보존 철학 강조 |
| **4** | 목록 탭 | 과거 흑돼지 일기 선택 ➔ 하단 [✨ AI 여행계획 생성] 클릭 ➔ **프롬프트 입력창에 기존 주소/본문이 꽉 채워져 있는 것(제로 타이핑)을 보여줌** | 인텐트를 활용한 강력한 편의성(UX) 및 AI 맞춤형 최적 동선 자동 생성 시연 |
| **5** | 일정 화면 | 생성된 장소 카드를 길게 눌러 상하로 드래그(이동)하고, 특정 장소를 왼쪽으로 스와이프(삭제) | 직관적인 편집 UI 및 데이터 찌꺼기 방지(고아 객체 완벽 소거)의 안정성 강조 |
| **6** | 목록/휴지통 | 목록 내 카드 우측 하단의 **휴지통 아이콘(🗑)을 클릭하여 인라인 삭제 시연** ➔ 친구 일기에서는 버튼이 숨김 처리됨 확인 ➔ 휴지통 진입 후 일괄 삭제 시연 | 개별/일괄 삭제 로직의 유연성과 접근 권한 분리(RBAC), View Type 필터링 방어 로직 어필 |
