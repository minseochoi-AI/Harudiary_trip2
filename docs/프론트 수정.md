# [목표] Harudiary AI 추천 및 외부 API 백엔드 이관 파이프라인 구현

기존 프론트엔드 중심의 하드코딩된 API 통신을 전면 백엔드로 이관하고, 사용자의 목적(현재 환경 맵핑, 내 주변 추천, 기록 기반 추천, 사용자 편집)에 따라 백엔드 오케스트레이션과 제미나이(Gemini) 지능화를 통합하는 구현 계획입니다.

## User Review Required

> [!WARNING]
> 본 플랜이 승인되면 기존 `Harudiary` 안드로이드 코드의 `KakaoLocalAPI.java`와 `WeatherAPI.java` 등 프론트엔드 통신 로직이 완전히 삭제되며, 모든 외부 통신 권한이 `travel` 백엔드 서버로 이관됩니다.

## 💡 [해결 방안] API 연동을 위한 구체적 파라미터 맵핑 및 분기 로직 (수정됨)

사용자님의 지적대로, 불확실한 제미나이(LLM) 텍스트 추출에 의존하는 대신 **프론트엔드(안드로이드)에 이미 구현된 `Record` 객체의 명시적 파라미터(`date`, `latitude`, `longitude`, `timeSlot`)를 100% 활용**하여 오케스트레이션을 제어합니다.

### 1. 프론트엔드 ➔ 백엔드 필수 전송 파라미터 (명시적 규약)
어떤 목적의 추천이든, 프론트엔드는 다이어리 작성/조회 UI에서 사용자가 명시적으로 선택한 아래의 값들을 백엔드로 보냅니다.
- `target_date`: 사용자가 DatePicker로 선택한 날짜 (YYYY-MM-DD)
- `lat`, `lng`: 디바이스 GPS 좌표 (또는 사용자가 지정한 목적지 좌표)
- `radius`: 검색 반경
- `query` (선택): 다이어리 본문 텍스트 (키워드 추출용)

### 2. 백엔드의 날씨 API 동적 분기 로직 (Date 기반)
백엔드는 수신받은 `target_date`와 현재 서버 시간을 수학적으로 비교하여 기상청 API를 완벽히 통제합니다.
- **`target_date` == 오늘(Today):** 즉각적인 날씨가 필요하므로 **`getUltraSrtNcst`(초단기실황)** 호출.
- **`target_date` > 오늘(Future):** 미래의 일정이므로 **`getVilageFcst`(단기예보)** 호출. (예보 API의 `base_date`와 `base_time`을 타겟 날짜에 맞춰 동적으로 세팅)

### 3. 카카오 API 호출 및 토큰 최적화 분기
- 제미나이에 수십 개의 장소가 들어가서 환각(Hallucination)이 발생하는 것을 막기 위해, 백엔드는 카카오 API(`search/category` 또는 `search/keyword`) 호출 후 얻은 결과에서 **'거리순(distance)' 상위 15개**만 절삭(Truncate)하여 제미나이 프롬프트에 주입합니다.

### 4. 제미나이 호출의 역할 재정의 (다이어리 기반 추천 시)
다이어리 기반 추천일 때, 날짜(`target_date`)는 이미 UI에서 넘어오므로 제미나이가 날짜를 찾을 필요가 없습니다. 
제미나이는 오직 **"다이어리 본문 텍스트에서 '제주도', '흑돼지' 같은 [지역/장소 키워드]를 정확히 뽑아내어 카카오 API 검색 쿼리(`query`)로 변환해주는 용도"**로만 1차 호출됩니다. 이후 날씨와 수집된 장소 데이터를 바탕으로 최적 동선을 짜는 2차 호출로 이어집니다.

# [Phase 6] 플랜 바 지도 연동 및 DB/오케스트레이션 통합 아키텍처

사용자님의 지적사항이 100% 맞습니다. LLM(제미나이)의 JSON 출력 스키마에 카카오맵 URL이나 위경도 좌표까지 강제로 응답하게 하는 것은 토큰 낭비, 응답 속도 저하, 환각(Hallucination) 위험을 초래하는 비효율적인 방식입니다. 
제미나이는 '추론과 최적 동선 도출'이라는 본연의 임무(이름, 시간, 수단, 카테고리)만 수행하게 하고, 정확한 메타데이터(URL, 좌표, 주소)는 백엔드 오케스트레이션 과정에서 원본 카카오 데이터나 DB를 매핑하여 채워넣는 것이 올바른 시스템 아키텍처입니다.

## 💡 Gemini JSON 통제 및 DB 연동 아키텍처 설명

현재 `GeminiClientService.java`는 사용자님이 제공하신 **`json.md`의 "구조화된 출력(Structured Output)" 명세**를 완벽하게 준수하여 `generationConfig`의 `responseSchema`를 통해 제미나이의 출력을 엄격히 제어하고 있습니다.
이 구조를 기반으로, 데이터 연동은 다음 파이프라인으로 이루어집니다.

1. **오케스트레이션 매핑 (In-Memory Join)**:
   - `GeminiOrchestrationService`가 카카오 API로부터 후보 장소 배열(`JsonNode`)을 가져올 때, 모든 메타데이터(URL, x, y, 주소)를 일시적으로 들고 있습니다.
   - 제미나이는 `json.md` 규격에 따라 최소한의 식별자(`place_name`)와 동선 정보만 반환합니다.
   - **백엔드 매핑 로직**: 제미나이가 반환한 `place_name`을 Key로 삼아, 원본 카카오 `JsonNode` 배열을 순회하여 매칭되는 장소의 `place_url`, `address_name`, `x`, `y` 값을 추출한 뒤 `PlaceDto`에 주입(Inject)합니다.
2. **프론트엔드 UI 렌더링 및 클릭 이벤트**:
   - 프론트엔드는 URL과 좌표가 꽉 채워진(Enriched) `PlaceDto`를 수신합니다.
   - 사용자가 플랜 바를 클릭하면 내장된 `place_url`을 통해 카카오맵으로 즉시 인텐트를 넘깁니다.
3. **DB 영구 저장 및 활용**:
   - 편집을 마친 사용자가 "저장"을 누르면 최종 리스트가 `POST /api/travel/plan/save`로 전달됩니다.
   - 백엔드는 이를 `Place` 엔티티로 변환하여 MySQL(`harudiary_db`)에 저장합니다. 이때 좌표와 URL도 함께 저장되므로, 추후 '내 여행 조회' 시 카카오 API 재호출 없이 완전한 플랜 바 UI를 그릴 수 있습니다.

> [!CAUTION]
> **SocketTimeoutException 폭탄 위험 (App0523에서 안 가져온 치명적 설정)**
> `Harudiary`의 `RetrofitClient.java`는 기본 통신 타임아웃(10초)을 사용하고 있습니다. 
> 제미나이 API가 일정을 생성하는 데는 평균 10~15초 이상이 걸립니다. 따라서 이대로 앱을 연동하면 100% **네트워크 타임아웃 에러**가 발생하며 앱이 뻗습니다.
> `App0523` 프로젝트의 `RetrofitTravelClient.java`에 적용되어 있던 **`OkHttpClient`의 1분(60초) 타임아웃 연장 설정**을 반드시 `Harudiary`로 가져와야 합니다!
