# 프론트엔드 기존 API 로직 및 엔드포인트 상세 분석 보고서

## 1. 기존 프론트엔드 API 로직 정리

| 기존 외부 API (프론트엔드) | 백엔드 이관 시 역할 (예정) | 프론트엔드 역할 (이관 후) | 사용자 목적 달성 |
|---|---|---|---|
| **카카오 로컬 (coord2address)** | 모바일에서 좌표를 받아 주소/건물명 텍스트로 변환하여 JSON화 | 백엔드의 단일 응답 JSON을 수신하여 텍스트 뷰에 즉시 렌더링 | 일기 작성 시 현재 내 위치(주소) 자동 기록 (수동입력 방지) |
| **기상청 초단기실황 (getUltraSrtNcst)** | 좌표를 기상청 격자(nx, ny)로 변환 후 현재 날씨/기온을 JSON화 | 백엔드의 날씨 상태를 수신하여 이모지 및 온도 텍스트 렌더링 | 일기 작성 시 당시 날씨와 온도를 자동 기록 (수동입력 방지) |

## 2. 현재 사용 중인 엔드포인트 개수 및 속성 분석

현재 프론트엔드(`Harudiary`)에 하드코딩되어 호출되는 외부 API 엔드포인트 총 개수는 **2개**입니다.

### 2.1 카카오 로컬 API (역지오코딩)
- **엔드포인트 개수**: 1개 (`https://dapi.kakao.com/v2/local/geo/coord2address.json`)
- **요청(Request) 속성**: 총 2개
  - `x`: 경도 (Longitude)
  - `y`: 위도 (Latitude)
- **사용 중인 응답(Response) 속성**: 총 4개
  1. `road_address.building_name`: 건물명 (존재 시 최우선 사용, 예: 서울특별시청)
  2. `road_address.unit_info`: 동/호수 상세 정보
  3. `road_address.address_name`: 도로명 주소 (단축 로직 적용)
  4. `address.address_name`: 지번 주소 (도로명 부재 시 대체)
- **사용 이유**: 사용자의 위경도 좌표(숫자)를 사람이 읽을 수 있는 유의미한 장소 텍스트로 변환하기 위함.

### 2.2 기상청 초단기실황 API (날씨)
- **엔드포인트 개수**: 1개 (`https://apis.data.go.kr/1360000/VilageFcstInfoService_2.0/getUltraSrtNcst`)
- **요청(Request) 속성**: 총 8개
  - `serviceKey`, `numOfRows`, `pageNo`, `dataType`, `base_date` (오늘 날짜), `base_time` (직전 정시 시간), `nx` (격자 X), `ny` (격자 Y)
- **사용 중인 응답(Response) 속성**: 총 2개
  1. `category == PTY` 의 `obsrValue`: 강수 형태 (0:맑음, 1:비, 3:눈 등) -> "☀️", "🌧️" 등의 이모지 변환에 사용
  2. `category == T1H` 의 `obsrValue`: 섭씨 기온 -> "27°" 형태의 텍스트 출력에 사용
- **사용 이유**: 다이어리에 현재 환경(날씨) 컨텍스트를 부여하기 위함.

## 3. 로직 증강을 위해 "빠진(누락된)" 엔드포인트 검토

현재 프론트엔드의 외부 통신 로직은 **"단순 현재 상태 표기(주소, 날씨)"**만을 목적으로 작성되어 있습니다. 따라서 논의하셨던 **"날씨 기반 자동 여행 위치 추천(제미나이 융합)"**을 달성하기에는 데이터가 부족(빠진 엔드포인트 존재)합니다.

- **빠진 엔드포인트 개수**: 1개 이상 (예상)
- **대표적 누락 기능**: **카카오 로컬 키워드 검색 API (`/v2/local/search/keyword.json`)**
- **필요성(이유)**: 날씨와 주소를 알았더라도, 그 주소 반경 1km 이내에 '어떤 실내 관광지'나 '어떤 카페/음식점'이 있는지(주변 장소 풀)를 백엔드가 알아야 합니다. 현재 `coord2address` 엔드포인트는 반경 내 장소 리스트를 제공하지 않고 오직 내 발밑의 주소 1개만 알려줍니다.

## 4. 응답 스키마 JSON과 백엔드 이관 시 구조화 방향

현재 프론트엔드에서는 응답값을 단순히 "서울 중구 태평로"라는 `String` 변수 하나, "27도"라는 `String` 변수 하나로 파싱해 UI에 뿌리고 끝냅니다. 
하지만 백엔드화 시에는 다음과 같이 각 외부 API 응답의 원본 속성들을 **하나의 통합 JSON 컨텍스트 블록**으로 구조화(정리)해야 합니다.

**[예상 구조화 응답 포맷 (백엔드 통합 후)]**
```json
{
  "user_context": {
    "location": {
      "raw_lat": 37.5665,
      "raw_lng": 126.9780,
      "formatted_address": "서울 중구 태평로1가"  // Kakao API 결과
    },
    "environment": {
      "weather_code": "0",  // Weather API 결과 (PTY)
      "temperature_celsius": 27.1  // Weather API 결과 (T1H)
    }
  },
  "recommendation_candidates": [] // 차후 주변 API 증강 시 삽입될 속성
}
```

> **준비 완료**: 현재 안드로이드 코드에 내포된 모든 외부 엔드포인트의 호출 방식, 개수, 목적, 속성을 낱낱이 파악했습니다. **지시하신 대로, 이 요소들을 어떻게 엮어 Gemini와 통신하는 API 파이프라인으로 확정 지을지에 대한 주도권은 사용자님께 넘깁니다.** 다음 증강 로직의 파이프라인 구상 방향을 말씀해 주시면 설계에 반영하겠습니다.
Kakao Developers 공식 문서(로컬 REST API 가이드)를 근거로, 카카오 로컬 API가 제공하는 전체 기능을 요청하신 체계적인 구조에 맞추어 재분류했습니다. 카카오의 로컬 API는 크게 텍스트 질의 중심의 '검색(Search)'과 GPS 좌표 중심의 **'지리/좌표 변환(Geo)'** 두 가지 카테고리로 나뉩니다.

### A. Search (장소 및 주소 검색)

사용자가 텍스트 형태로 입력한 데이터를 기반으로 위치 정보를 찾는 기능입니다.

1. **SearchAddress:** 주소 검색 (텍스트 주소 → 좌표 변환)
2. **SearchKeyword:** 키워드로 장소 검색 (검색어 → POI 목록)
3. **SearchCategory:** 카테고리로 장소 검색 (업종 코드 → POI 목록)

### B. Geo (좌표 기반 지리 변환)

디바이스의 센서(GPS)나 지도 클릭 등을 통해 얻은 '좌표'를 실생활의 텍스트 정보나 다른 체계로 변환하는 기능입니다.
4. **CoordToRegionCode:** 좌표로 행정구역정보 받기 (좌표 → 법정동/행정동)
5. **CoordToAddress:** 좌표로 주소 변환하기 (좌표 → 상세 번지수)
6. **Transcoord:** 좌표계 변환하기 (A 좌표계 → B 좌표계 변환)

---

### [카카오 로컬 API 기능 분류 표]

로컬 API의 각 기능이 어떤 데이터를 요구하고(Request), 어떤 결과를 반환하는지(Response) 원자적으로 식별하여 정리한 명세입니다.

| 카테고리 | 항목 번호 및 명칭 (엔드포인트) | 동작 방식 및 데이터 획득 근거 (Request ➔ Response) |
| --- | --- | --- |
| **A. Search**<br>

<br>(텍스트 기반 검색) | **1. 주소 검색**<br>

<br>(`search/address`) | 사용자가 직접 텍스트로 입력한 지번/도로명 주소를 분석하여, **정확한 위도/경도 좌표(X,Y)**와 구조화된 우편번호, 건물명 등으로 분리 반환. |
|  | **2. 키워드로 장소 검색**<br>

<br>(`search/keyword`) | "맛집", "약국" 등 사용자가 입력한 자유 형식의 질의어(Query)를 분석하여 관련된 **관심 장소(POI) 목록**(상호명, 연락처, 상세 주소, 거리)을 배열 형태로 반환. |
|  | **3. 카테고리로 장소 검색**<br>

<br>(`search/category`) | 카카오가 내부적으로 지정한 **특정 업종 코드**(예: FD6=음식점, CE7=카페, CS2=편의점)를 입력받아, 지정된 좌표 반경 내에 존재하는 해당 카테고리의 장소 목록만 필터링하여 반환. |
| **B. Geo**<br>

<br>(좌표 기반 변환) | **4. 좌표로 행정구역정보 받기**<br>

<br>(`geo/coord2regioncode`) | 기기의 센서로 획득한 위경도 좌표를 바탕으로, 해당 위치가 속한 대략적인 **행정동 및 법정동 이름**을 반환. (예: 지역 기반 날씨 서비스나 상권 연계에 주로 사용) |
|  | **5. 좌표로 주소 변환하기**<br>

<br>(`geo/coord2address`) | 입력받은 위경도 좌표를 실생활에서 사용하는 **정확한 지번 주소(~~번지) 및 도로명 주소** 텍스트로 맵핑하여 반환. |
|  | **6. 좌표계 변환하기**<br>

<br>(`geo/transcoord`) | WGS84, WTM, TM 등 서로 다른 시스템 간의 지리적 **좌표계 포맷을 상호 연산하여 변환**. 공공 데이터(예: 기상청 데이터의 WTM 좌표)를 카카오맵(WGS84) 규격에 맞게 렌더링할 때 필수적으로 사용. |

### [API 활용 인사이트 분석]

* **환경 컨텍스트 자동 맵핑 (B-4, A-3의 결합):** 스마트폰이나 웨어러블의 GPS 데이터를 `CoordToRegionCode`로 넘겨 행정동을 파악하고, 이를 공공 기상청 API의 '동네 날씨 지수'를 가져오는 연결 고리로 활용할 수 있습니다. 동시에 백그라운드에서 `SearchCategory`를 실행해, 사용자가 주로 컨디션 난조를 겪는 장소(특정 식당, 카페 등)를 데이터베이스에 자동으로 누적시킬 수 있습니다.
* **수동 입력의 최소화 (B-5 활용):** 사용자가 앱에 데이터를 기록할 때 위치를 일일이 타이핑할 필요 없이, `CoordToAddress` 기능이 획득한 정확한 주소 텍스트를 SQLite에 즉각 `INSERT`하여 사용자 편의성과 데이터 정확도를 대폭 끌어올릴 수 있습니다.

# 카카오 18종 카테고리 그룹 및 UI 템플릿 맵핑 명세서

> 프론트엔드 UI의 동적 템플릿(색상, 아이콘 분기) 처리를 위해 카카오 로컬 API가 반환하는 `category_group_name` 18종을 5가지 대분류로 통합하는 명세입니다.

## 1. UI 템플릿 카테고리 매핑 규칙 (5대 그룹)

| 분류 그룹 | 대상 카카오 카테고리 (18종) | 프론트엔드 테마 속성 |
| :--- | :--- | :--- |
| **식도락** | `음식점(FD6)`, `카페(CE7)` | 연한 주황 배경, 포크 아이콘 (`lunch`) |
| **관광/문화** | `관광명소(AT4)`, `문화시설(CT1)` | 연한 파랑 배경, 카메라 아이콘 (`morning`) |
| **숙박/휴식** | `숙박(AD5)` | 연한 보라 배경, 침대 아이콘 (`evening`) |
| **교통/편의** | `주차장(PK6)`, `지하철역(SW8)`, `편의점(CS2)` | 연한 녹색 배경, 지하철/기차 아이콘 (`icon_background`) |
| **기타** | `대형마트(MT1)`, `어린이집, 유치원(PS3)`, `학교(SC4)`, `학원(AC5)`, `주유소, 충전소(OL7)`, `은행(BK9)`, `중개업소(AG2)`, `공공기관(PO3)`, `병원(HP8)`, `약국(PM9)` | 흰색/연회색 배경, 기본 아이콘 (`gray_label`) |

## 2. 데이터 통합 로직 (Category Orchestration)
- **Primary Input:** 사용자의 현재/목표 위경도 좌표 및 다이어리 컨텍스트.
- **API Pipeline:** 백엔드가 카카오 API에서 주변 반경 장소를 검색할 때 `category_group_name`을 추출하여 제미나이 컨텍스트로 전달.
- **제미나이 스키마 제어:** JSON Schema의 `enum` 속성을 활용해 제미나이가 임의의 카테고리를 창작하지 못하도록 차단하고, 위 5개 그룹 혹은 카카오 18개 카테고리명 중 하나에 정확히 매핑하도록 강제함.

## 5. 실제 터미널 호출을 통한 엔드포인트 검증 결과 (총 8개)

지시하신 대로 카카오 API 6종과 기상청 API 2종, **총 8개의 엔드포인트**를 서버 터미널에서 `curl`로 직접 호출하여 반환되는 실제 JSON 스키마와 속성을 전수 검증했습니다.

### [카카오 로컬 API - 총 6개]
| 분류 | 엔드포인트 | 호출 검증 상태 | 검증된 핵심 Request 속성 (개수) | 파싱 가능한 핵심 Response 속성 (개수) |
|---|---|---|---|---|
| Search | `search/address` | ✅ 정상 | `query` (1개) | `address_name`, `x`, `y` (3개) |
| Search | `search/keyword` | ✅ 정상 | `query`, `x`, `y`, `radius` (4개) | `place_name`, `category_name`, `distance`, `road_address_name`, `x`, `y` (6개) |
| Search | `search/category` | ✅ 정상 | `category_group_code`, `x`, `y`, `radius` (4개) | `place_name`, `category_name`, `distance`, `road_address_name`, `x`, `y` (6개) |
| Geo | `geo/coord2regioncode` | ✅ 정상 | `x`, `y` (2개) | `region_type`, `address_name`, `region_1depth_name`, `region_2depth_name`, `region_3depth_name`, `code` (6개) |
| Geo | `geo/coord2address` | ✅ 정상 | `x`, `y` (2개) | `road_address.building_name`, `road_address.address_name`, `address.address_name` (3개) |
| Geo | `geo/transcoord` | ✅ 정상 | `x`, `y`, `input_coord`, `output_coord` (4개) | `x`, `y` (2개) |

### [기상청 단기예보 API - 총 2개]
| 분류 | 엔드포인트 | 호출 검증 상태 | 검증된 핵심 Request 속성 (개수) | 파싱 가능한 핵심 Response 속성 (개수) |
|---|---|---|---|---|
| 날씨 | `getUltraSrtNcst` (초단기실황) | ✅ 정상 | `serviceKey`, `numOfRows`, `pageNo`, `dataType`, `base_date`, `base_time`, `nx`, `ny` (8개) | `category` (PTY, T1H 등), `obsrValue` (2개) |
